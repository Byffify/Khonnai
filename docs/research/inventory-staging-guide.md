# ร้านบน Supabase สำหรับทดสอบ

18 ตุลาคม2026. `/shop` ใช้บัญชีจริงและฐานข้อมูล staging ของ Khonnai ส่วน `/app` ยังเป็นเดโมในเครื่อง ไม่ใช่ข้อมูลร้านบนบัญชี การเปิดร้านไม่อ่าน นำเข้า หรือเขียนทับ `micro-erp-v1` ผู้ใช้อนุญาตให้เริ่มร้านว่าง เพราะข้อมูลในเครื่องเป็นเดโม

## เปิดใช้งาน

```powershell
cd D:\Khonnai
npm.cmd run auth:dev
```

เปิด [หน้าบัญชี](http://127.0.0.1:5293/auth) เข้าสู่ระบบ แล้วกด **เปิดร้านของคุณ** เพื่อไป [ร้านบนบัญชี](http://127.0.0.1:5293/shop) เริ่มจากเพิ่มสินค้า ใส่ไซซ์/สี ยอดเริ่มต้นและราคา แล้วบันทึก เปิดอีกหน้าต่างเข้าสู่บัญชีเดียวกันเพื่อตรวจข้อมูลที่บันทึกไว้

ออกจากระบบได้จากหน้าตั้งค่า เมื่อตรวจพบว่าบัญชีเปลี่ยนหรือ session ใช้ไม่ได้ หน้าเว็บจะปิดข้อมูลร้านเดิมก่อนเปิดบัญชีถัดไป ไม่ส่งรายการค้างไปยังบัญชีใหม่

ในตั้งค่า → **บัญชีและความปลอดภัย** ดูอีเมลที่เข้าสู่ระบบและกด **ส่งลิงก์เปลี่ยนรหัสผ่าน** ได้ ระบบส่งคำขอไปยังอีเมลของบัญชีที่ตรวจแล้ว เปิดลิงก์ในอีเมลเพื่อยืนยันตัวตนก่อนตั้งรหัสใหม่ พร้อมกรอกยืนยันรหัสผ่านและผ่านเงื่อนไขทั้ง4ข้อ หลังเปลี่ยนสำเร็จให้เข้าสู่ระบบใหม่ การส่งอีเมลขึ้นกับการตั้งค่า Auth/email เดิมของ staging

ข้อมูลร้านต้องเชื่อมต่ออินเทอร์เน็ตเพื่อบันทึก หากคำตอบหลังบันทึกหายไป ระบบจะหยุดรายการใหม่และให้กด **ตรวจสอบรายการเดิม** ระบบตรวจรหัสรายการก่อนส่งซ้ำเพื่อไม่ออกบิลซ้ำ หากบังคับปิดหรือรีเฟรชหน้า คำสั่งค้างในหน่วยความจำจะหายไป ให้ตรวจยอดและประวัติล่าสุดก่อนกรอกรายการใหม่ ไม่มีคิวขายออฟไลน์

## สิ่งที่เชื่อมแล้ว

สินค้าและรูป ไซซ์/สี รับเข้า ปรับยอด ขาย แก้และยกเลิกบิล จอง ยกเลิกจอง แปลงจอง รับคืน เปลี่ยนสินค้า ข้อมูลร้าน และประวัติการเคลื่อนไหว ใช้กติกา `execute` เดิมบนเซิร์ฟเวอร์พร้อม transaction ของฐานข้อมูล หน้าจอแสดงบันทึกสำเร็จเมื่อได้รับผล commit แล้วเท่านั้น

RLS บังคับแยกข้อมูลตามเจ้าของร้านทุกตาราง Foreign key ที่รวมรหัสร้านป้องกันการอ้างสินค้าอีกหนึ่งร้าน การล็อกแถวร้านประสานคำสั่งจากหลายเครื่องและการออกเลขบิล คำสั่งมีรหัสและ digest สำหรับตรวจซ้ำก่อนตรวจ revision ไม่รับทั้งก้อนข้อมูลร้านหรือรหัสเจ้าของจากเครื่องผู้ใช้เป็นคำสั่งบันทึก

รูปสินค้าเก็บเป็นข้อมูลภาพในตารางส่วนตัวบน Supabase Postgres ยังไม่ได้ใช้ Storage bucket รูปแบบนี้รักษารูปในไฟล์สำรองและตัวสร้าง PNG เดิมได้ ทั้งร้านยังมีขีดจำกัดข้อมูลเดิมประมาณ4.5ล้านตัวอักษร และเขียนกราฟข้อมูลใหม่ใน transaction ต่อคำสั่ง จึงเป็นขอบเขต MVP สำหรับ staging ไม่อ้างการรองรับข้อมูลจำนวนมาก

ดาวน์โหลดไฟล์สำรองได้จากตั้งค่า → สำรองข้อมูล การนำไฟล์กลับเข้าร้านบน Supabase ยังไม่เปิดใช้ ไม่มีการล้างร้านหรือเขียนทับด้วยข้อมูลในเครื่อง เมนูนำเข้าเดิมของ `/app` ยังคงอยู่

## การตรวจที่รันได้ซ้ำ

```powershell
npm.cmd test
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run test:browser
```

สำหรับผู้พัฒนาเท่านั้น หลังติดตั้ง migration และเปิด `auth:dev` ไว้:

```powershell
node scripts/verify-inventory-runtime.mjs
node scripts/verify-inventory-runtime.mjs --browser
```

ตัวตรวจสร้างบัญชีสังเคราะห์และร้านแยกที่ระบุด้วย UUID สุ่มใหม่ ไม่ใช้บัญชีเดิมเป็น fixture และ cleanup เฉพาะ UUID ที่สร้างในครั้งนั้น บัญชีสังเคราะห์ยืนยันอีเมลด้วย SQL จึงไม่พิสูจน์การส่งอีเมลจริง แบบ `--browser` ต้องมี Chromium ของ Playwright และบริการ5293/5294 ผลอยู่ที่ `outputs/inventory-staging/live-verification.json` และภาพใน `outputs/inventory-staging/browser/`

Migration `20261018134456_cloud_inventory.sql` ทดสอบ DDL/RLS/FK ใน transaction ที่ rollback ทั้งหมดก่อนใช้ CLI เพิ่ม schema จริง ผล preflight และการติดตั้งอยู่ใน `outputs/inventory-staging/migration-{dry-run,applied}.json` สคริปต์ `migrate-inventory-staging.mjs --apply` ตรวจ proof hash ก่อนเพิ่ม schema และตรวจประวัติที่ติดตั้งแล้วเมื่อรันซ้ำ ห้ามเปลี่ยน migration ที่ใช้แล้ว

## ขอบเขตการเปิดใช้งาน

ยังไม่ deploy production และยังไม่เปลี่ยน CTA บน landing บัญชีที่สร้างใน staging จัดเป็นทีมเพื่อไม่ปะปนกับหลักฐานผู้ใช้จริง บัญชีพรีเซนต์ การจัดข้อมูลเดโม รายงานจำนวนผู้ใช้จริง และการเปิด HTTPS สำหรับภายนอกยังเป็นงานถัดไป อย่าอ้างว่าล็อกอินได้เท่ากับมีการใช้งานสต็อกจริง

ใช้หลัก Model the Domain โดยรักษา `State/Command` เดียวกันทั้งโฟลว์ ใช้ Make Operations Idempotent โดยตรวจ command receipt ก่อนทำรายการซ้ำ และใช้ Prove It Works โดยตรวจฐานข้อมูลและเว็บจริงแยกจาก unit tests
